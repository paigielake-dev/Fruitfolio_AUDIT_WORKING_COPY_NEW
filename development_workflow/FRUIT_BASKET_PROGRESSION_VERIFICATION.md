# Reset-safe progression and protected game persistence

The old reset only changed the visible level to one. The next success recalculated the level from lifetime successful rounds, immediately restoring a high level. Current progression now has an optional per-level success counter, resets it with the catching level, and keeps lifetime wins, highest level, fruit, stars and scores. New progression preserves the existing thresholds (2/2/2/3/3/4/4 successful rounds per advancing tier) and existing cap eight. Failed attempts do not increase difficulty or consume earned success credit. After reaching the cap, configuration and per-level progression stop increasing. Question difficulty remains a separate input.

Legacy JSON without the counter stays unchanged on read. When lifetime wins and the visible level agree with the original algorithm, their existing tier offset can continue. If they disagree (for example a legacy reset), the visible level is retained and new credit starts from that level rather than guessing a reset date or jumping to lifetime difficulty. No historical scores/catches are reconstructed. Computational caps/gradual ranges are tested; physical-device playtesting is still required before claiming a “tested maximum” or cozy experience.

The existing game JSON/defaults key is preserved behind a Foundation persistence adapter. Missing data is distinct from wrong stored types, undecodable bytes, unsupported explicit format versions, invalid counters and data changed/cleared since loading. Those cases block writes and retain original data. Explicit reload reads current state without a migration write; it cannot silently resurrect a cleared stale copy. The UI pauses play/pending questions and presents a scrollable recovery view, with no destructive reset or fake empty-progress claim. The snapshot comparison detects tested sequential stale writers; UserDefaults is not represented as a cross-process atomic transaction or physically verified disk/crash durability.

Eight production persistence regressions and five progression regressions cover actual UserDefaults reinitialization, original byte preservation, stale writes, deletion, old/new format handling, reset-after-200-wins through storage, failure credit and cap/difficulty independence. Reinitialization within tests is not a physical app restart. Existing Apple-only classification consequence tests now drive the shared entry/settlement clock before expecting awards, matching the changed source semantics; their Apple execution remains NOT RUN.

Apple build, recovery-screen focus/scroll, multiwindow behavior and physical playtesting remain unavailable. Actual captured round-result/fruit/star/consequence summaries continue in the next source-order batch (366–367); this document does not mark those requirements complete.
